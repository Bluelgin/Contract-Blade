# 契约武器救援：优化与性能测量

测量日期：2026-10-06。范围仅为契约武器破坏后的救援队列，不涉及黑狐战斗。

## 本次优化

在事件驱动救援的基础上，收紧存档变更标记：

- 相同破坏事件重复到达，且没有新数据时，不重复标记存档需要保存。
- 队列等待确认期、等待重试、轮转检查时，不重复标记存档需要保存。
- 新任务、快照升级、旧任务获得真实破坏事件、任务取消、恢复完成、重试时间变化，仍标记保存。

没有新增全局武器缓存、世界容器扫描或另一套定时器。救援上限保持每轮检查 32 个任务、每玩家每 tick 最多恢复 2 位女仆、全服每 tick 最多恢复 8 位。

注意：SavedData 的 dirty 标记会合并至存档写入。因此减少 1,000 次标记，不代表减少 1,000 次磁盘写入。

## 方法

使用同一测试代码，分别启动优化前、优化后的独立 Forge 服务端 JVM，在隔离世界执行。环境为 Java 17.0.20.1、1 GiB 最大堆、12 个可用逻辑处理器，加载本模组、车万女仆、拔刀剑及测试所需依赖。

- 轻量路径先预热，再测 31 批；每批 250 或 1,000 次调用。
- 实际恢复使用原生女仆创建、契约数据解码、显现及解绑；2 轮预热，5 轮测量。
- 大数据样本在原生女仆 NBT 中加入 256 KiB 固定种子随机字节，编码后物品约 264 KB。它用于测解码/恢复开销，不代表复杂装备或 AI。
- 恢复计时包含现有日志；队列构建、快照编码、清理不计入恢复耗时。
- 在服务端线程使用单调时钟计时，并记录该线程分配的字节数。恢复测试直接推进测试世界时钟，不等待真实 tick。

## 结果

轻量调用的中位数：

| 场景 | 优化前 | 优化后 | 优化后分配量/次 |
| --- | ---: | ---: | ---: |
| 无任务的队列查询 | 0.050 µs | 0.051 µs | 0 B |
| 空背包玩家完整 5-tick 维护入口 | 3.920 µs | 4.055 µs | 3,784 B |
| 32 个等待任务的队列处理 | 1.446 µs | 2.110 µs | 2,304 B |
| 重复破坏事件，小快照 | 0.517 µs | 0.480 µs | 128 B |
| 重复破坏事件，256 KiB 快照 | 0.435 µs | 0.416 µs | 128 B |

无效 dirty 标记：等待处理、重复事件各执行 1,000 次，均从 **1,000 次降至 0 次**。

真实恢复（每次处理 2 位女仆）：

| 场景 | 前：中位数 | 后：中位数 | 后：P95 | 后：最大单次 | 后：分配量/次 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 32 位普通女仆批量恢复 | 1.312 ms | 1.401 ms | 1.858 ms | 5.199 ms | 465,056 B |
| 16 位携带 256 KiB 数据的女仆批量恢复 | 1.413 ms | 1.523 ms | 2.134 ms | 2.312 ms | 1,502,944 B |

优化后整批累计处理时间中位数分别为 22.399 ms（32 位）和 12.758 ms（16 位）。这是累计 CPU 路径耗时，不是玩家等待时间：正式游戏仍分轮执行，不会把整批工作挤入一 tick。

## 判断与边界

本次确实消除了不必要的存档变更标记，但没有测出明显的 CPU 提速；微秒级差异以及恢复路径的小幅变化不能作为提速证据。真实恢复的主要开销仍为数据解码和实体恢复，且已有分批预算。

此次不是整服 TPS、复杂女仆 AI、多人混合负载或长期 GC 压测，不能据此保证任何整合包的 TPS，也不能推导“多少把武器才崩服”。线程分配量不是常驻内存占用。

测试入口默认关闭：`-PcontractPerfTest=true -PcontractPerfLabel=before|after`。原始数据保存于 `tmp/carrier-performance-before.json`、`tmp/carrier-performance-after.json`。轻量路径 JSON 中的 P95 是批次平均值的 P95，不是逐次调用 P95。

## 正确性验证

新增原生服务端回归检查：事件入队、重复事件不替换快照、等待不标记保存、同绑定取消、快照升级、失败后的重试时间、旧任务升级以及存档往返。

另行执行现有复活/破坏事件回归，覆盖拔刀剑折断仍可显现与收回、武器转移到容器不触发救援、真实破坏事件救援、32 把独立武器批量恢复以及全服恢复预算。
